# X86: re-measure of the landed wins on x86-64

- Date: 2026-10-31. Kind: re-measure on x86-64 of the performance wins landed on arm64 in the October 2026 performance and
  correctness work, with a follow-up on the two rows that regressed (read-only).
- Repos: url-parser, fst, docset, queue, repr, datetime, strings at `main` as cloned or pulled on 2026-10-31; the source
  records no commit heads.
- Machines: a shared Linux x86-64 VM (g++ 11.2), Apple M4 Pro (Apple clang 17), Intel Core i9-9980HK (follow-up; Apple
  clang 17 and gcc 16.2). Method: [PERFORMANCE.md](../PERFORMANCE.md).
- Resolution checked against each repo's default branch on GitHub on 2026-11-01.

## Arm-only wins and x86 regressions
- **Arm-only:** docset bitmap AND at density 0.1 (3.6x on arm, 1.0x on x86). Likely cause: the "two bits per word without a branch" array extraction
  helps Apple's branch predictor/ctz path; on x86 the cost is elsewhere (x86 old absolute is 1.55 ms vs arm 0.95 ms and new 1.56 ms vs 0.26 ms). Profile the x86 path before claiming the win cross-platform.
- **Arm-heavier:** repr (about half the gain on x86), datetime `2020/01/02` (23x vs 77x), url-parser 256 B 25% escapes loses to the LUT decoder on x86.
- **x86 regression:** docset `andnot` dense bitmaps about 7% slower (reproduced 3 times).
- **Needs a quiet re-run:** queue at 4x4 / 8x8.

## Caveats
- gcc 11 against Apple clang 17; different compilers as well as different ISAs. A clang build on the VM (clang 12) was not tried.
- The VM is shared (about 40 users); pinning to one core removes migration but not cache/memory contention. A/A rows inside each bench were 0.99-1.01 except where noted.
- strings and datetime-format rows need a newer toolchain on the VM (gcc 13+ or clang 17+ with libstdc++ 13).

## Follow-up: queue and docset on x86, interleaved (2026-10-31)

Host for timing: the Intel Core i9-9980HK (macOS, Apple clang 17 and gcc 16.2, under an exclusive timing hold); the Linux VM (load 3 to 19) only for ASan/TSan and one cross-check. Every ratio is the median of per-round ratios from an interleaved run with an A/A column (the same code twice, 0.98 to 1.02 here).

- **queue 4x4 / 8x8 at 0.64x to 0.8x: not a Linux effect, real on Apple clang.** On the Linux VM (g++ 11, four pinned cores) the earlier numbers came from non-interleaved best-of-3 runs; three in a row gave 0.53, 0.48 and 2.36 at 8x8, and the interleaved ratio was 1.0 (4x4) and 1.06 (8x8) with 1x1 at 0.77. On the i9 with Apple clang the queue was 0.92, 0.71, 0.57 and 0.55 of the baseline at 1x1 to 8x8. Cause: the four hot operations were out-of-line templates calling an out-of-line `_push_wait` with a `unique_lock&`, not the waiter counting, layout or notify (ablated one by one). Fixed in `queue` (`_push_room()`, `QUEUE_HOT`, release store for the count): Apple clang 1.16 to 1.25x, gcc 16 1.25 to 1.47x, arm64 1.24 to 1.96x, Linux VM 0.93 to 1.24x of the baseline.
- **docset `andnot` on dense bitmaps 7% slower: not reproduced.** Interleaved old / head / work, densities 0.1 to 0.5: ANDNOT within +-3% of the reference on x86 (clang, gcc 16) and arm64. The 7% that did reproduce: arm64 ANDNOT of two array containers at density 0.03 (0.935x, from the conversion inlined into the callers; fixed by making it out of line), and the x86 bitmap AND at density 0.1 (0.91x on clang, from the branch-free extraction without BMI1). Fixed in `docset` (extraction by CPU and size): AND at 0.1 is 2.27x (clang) and 2.47x (gcc 16) on x86 and 3.52x on arm64; at 0.2 1.86x, 2.21x and 2.81x (arm64 was 0.90x).
- Still open: array-array AND at density 0.03 reads 0.92x to 0.93x on gcc 16 for both the previous and the new header (clang: 0.98x); the code path is unchanged, so it looks like layout or inlining in the gcc build, not examined further.
