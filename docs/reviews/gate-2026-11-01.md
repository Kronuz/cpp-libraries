# Gate: start against head, 2026-11-01

- Date: 2026-11-01, measured from 09:30 to 13:55 PST. Kind: the closing gate of the October 2026
  performance and correctness work, measured read-only: no library code changed for it.
- Question (owner): is every library in a substantially better position than at the start, and is
  any one slower than it was?
- Repos: the 51 in the table below. uinteger_t and base-x had their own campaign and
  [record](2026-10-31-uinteger_t-base-x.md); the rest of the catalog is not in this gate.
- Machines: Apple M4 Pro and Intel Core i9-9980HK ([PERFORMANCE.md](../PERFORMANCE.md), section 2).
- Status of the slow rows checked against each repo's default branch on GitHub on 2026-11-01 at
  16:40 PST.

## Answer

Head is faster than start by 3% or more in geometric mean on both machines in 35 of the 51
repositories, and on one machine with the other level in 3 more (bitpack, htm, lru-cache). Nine
are level on both machines, within 3%: bloom-filter, char-classify, errno-names, flume, math,
radix-router, split, storage and time-point.

Four are slower on both machines, each for a correctness fix:

- **fs** (0.835 M4, 0.763 i9): the `normalize_path` rewrite. Fixed since the gate in `fs:c91b457`
  and `fs:f4439d8`, re-timed so far on an Apple M1 Pro.
- **enum-reflection** (0.864, 0.838): a name lookup compares the name on a hash hit, where start
  accepted a forged string with a member's hash.
- **io** (0.935, 0.959): `io::pread` loops to the full count, so a read that ends at end of file
  makes a second call. Without that row: 0.988 and 1.014.
- **stringified** (0.797, 0.849): copies and moves no longer dangle, and `c_str()` of a bare view
  copies once. Without the rows whose behavior changed: 1.054 and 1.197.

151 rows in 29 repositories are below 0.97 outside the A/A spread. Each is listed under
[Slower rows](#slower-rows) with its cause and status: fixed since the gate, an accepted cost of a
fix, the placement of unchanged code, a row that measures different behavior, a fix in progress,
or open.

## Method

- **START** is the commit before the campaign's first change in that repository: the last commit
  on its default branch before 2026-10-30 (`git log --before=2026-10-30T00:00 -1 origin/main`).
  **HEAD** is the default branch when its gate run started. Both are in the scoreboard.
- **What runs.** HEAD's bench sources (`bench/` or `benchmarks/`), built twice from one tree: once
  with START's library sources and once with HEAD's, the same compiler, flags and dependency pins
  on both sides. A row that needs API added after START is dropped and named in the report. A repo
  without a bench (errno-names, fs, io, math, stringified, time-point, times) gets a micro-bench of
  its hot entry points written for the gate; http adds a request-parser micro-bench and a `wrk`
  end-to-end run, because its bench uses API that start lacks.
- **Build.** Apple clang 17.0.0, CMake Release (`-O3 -DNDEBUG`), on both machines. Every M4 Pro
  binary is checked with `file` to be arm64 before it is timed.
- **Runs.** Each round runs START, HEAD and START again (the A/A control, a second copy of the
  START binary), one after another, inside one exclusive hold of the machine of at most 10
  minutes; 3 to 15 rounds a row. `tools/ab_compare.py` reports each row's ratio START time / HEAD
  time, the median of the paired rounds, so above 1 means HEAD is faster; its A/A deviation, the
  largest |A/A - 1| over the rounds; and the geomean over the repo's library rows. Control rows
  (code neither side changed) are reported apart.
- **A slower row** is one with a ratio below 0.97 whose distance from 1 is larger than its A/A
  deviation.
- **Not comparable.** A row where HEAD gives a different result by design (a behavior fix) does
  different work; it is reported apart and named under the repo.

Geomeans that need a word:

- **repr** (4.399, 3.854) counts the `max_size=64` rows on 4 KB and 64 KB inputs, where head skips
  the elided middle instead of walking it; without them 3.189 and 2.808. **strict-stox** (1.753,
  1.518) counts `stod` of 800 digits, which start truncated at 63 bytes; without it 1.820 and
  1.578.
- **string-similarity** (20.801, 23.165) is over the rows whose answers did not change; over every
  row, 18.696 and 19.459. Jaro, Jaro-Winkler, Sorensen-Dice and the phonetic metric give corrected
  scores at head.
- **cuuid** (2.269, 1.970) counts two rows that hit head's compact-v1 cache; without them 1.294 and
  1.278.
- **htm** on the M4 Pro is over 9 of 14 rows: 161 of 20,000 ids differ there (start's
  floating-point contraction, fixed), so the rows that use them are void. Over all 14, 1.062.
- **compressors** is over 167 rows; its one-shot calls (1.750, 1.868) are a new design, the
  stream classes 1.122 and 1.066, the block API 1.005 and 0.996.
- **sha256** is level on the kernels (1.002, 0.996) and faster on the hex-string API (2.797,
  1.241).
- **http**'s end-to-end run (`wrk`, keep-alive) compares two different stacks: head has coroutine
  handlers, cancellation, a read-ahead watch, a body cap, a newer reactor and the hardened
  http-parser.

## Slower rows

Status words: **fixed** (`repo:sha`, with the numbers that show it), **accepted** (the cost of a
fix, and why it stays), **placement** (the code is unchanged and the row moves with where the
linker puts it), **not comparable** (head does different work by design), **fix in progress**,
**open** (unexplained, or with an issue).

**allocators** (M4 1, i9 1)
- i9 `pool_direct` steady state (allocate one block, free it) 0.352: cause not isolated. Fix in
  progress.
- M4 `vector<int>` n=1000 0.963: accepted. `construct`'s `noexcept` clause follows the element's
  constructor (the forwarding fix), a few percent of a 0.5 ns operation; in the CHANGELOG.

**bitpack** (M4 6, i9 10)
- M4 `scalar` widths 8, 18, 20, 21 and 24 (0.815 to 0.940): placement. `unpack_scalar` is
  unchanged and all 33 instantiations have identical machine code in both binaries.
- M4 `simd` width 5 (0.911, 0.844 in a second hold): placement. The same kernel reads 1.029 in
  `bitpack_unpack_alias`.
- i9, 10 rows from 0.931 to 0.969: noise. The i9 START and HEAD binaries are the same bytes.

**bloom-filter** (i9 2)
- i9 `N=8192 keylen=16` `add` 0.900 and `hit` 0.940: placement. The source of `BloomFilter` is
  unchanged; the i9 shows up to 12% between builds of the same code.

**btree** (M4 5, i9 1)
- M4 `map<u64,u64>` `find` n=100,000 0.966, `set<u64>` copy and erase n=100,000 0.966,
  `map<u64,u64>` `insert` n=1,000 0.967, `insert-erase` with 16-byte keys 0.968: open, within 3.4%;
  the change touches slot construction and relocation, not search. No issue filed.
- M4 `ownership_bench` `move-construct` 0.500: noise. A root-pointer transfer of microseconds,
  with an A/A deviation of 60%.
- i9 `map<u64,u64>` `iterate` n=1,000 0.922: placement. The iterator is unchanged, and the same loop
  over `set<u64>` reads 1.124.

**cartesian** (M4 2, i9 1)
- M4 `Cartesian(lat, lon, h, DEGREES)` WGS84 0.874 and OSGB36 0.899, i9 `operator==` 0.860:
  placement. `cartesian.cc`'s instruction streams are identical at start and head; each row reads
  about 1.0 on the other machine.

**compressors** (M4 1)
- M4 `xxh32 n=256 one-update` 0.639: fixed in `compressors:430870c`. Short updates run in one NEON
  register: 256 B in one update took 10.8 ns before `533bee4`, 16.7 ns at the gate's head and 7.5 ns
  now (M4 Pro). A hash that waits for the previous digest is slower, 26.2 ns before `533bee4` and
  38.0 now: open, [compressors#5](https://github.com/Kronuz/compressors/issues/5).

**crc32c** (i9 1)
- i9 `hw (crc32c) 16 B` 0.957: placement. The control `instruction loop 16 B` reads 0.936 in the
  same runs.

**cuuid** (i9 1)
- i9 `cuuid_compare` v1 without compaction 0.945: placement. The same operation reads 1.000 in
  `cuuid_v1_bench` in the same hold.

**docset** (M4 4, i9 2)
- AND of two bitmaps with 40 members per chunk (M4 0.843), 80 (M4 0.919), ANDNOT with 40 (M4
  0.900): above `extract_loop_max` (32 on arm64) head takes the branch-free extraction. Fix in
  progress.
- AND with 20 members per chunk (M4 0.955, i9 0.819) and 40 (i9 0.930): the array conversion moved
  out of line (`container::fill_array`), about 28 ns per chunk; the size on the i9 is unexplained.
  Fix in progress.

**enum-reflection** (M4 6, i9 7)
- `enum_type` hits on 8- to 128-member enums and on `Status` and `Method` (M4 0.483 to 0.759, i9
  0.422 to 0.755): accepted. A hit compares the name, ASCII case-insensitively, after the hash
  matches; start returned a member for any 15-byte string built to share its 64-bit hash. A faster
  check is in progress.
- i9 `enum_name` of a 128-member dense enum 0.879: open. The change does not touch it, and the 8- and
  32-member rows read 1.05 and 0.99. No issue filed.

**flat-map** (M4 1, i9 1)
- i9 `<i8,u64>` n=100 `find`, keys replayed in one order, 0.758: accepted (CHANGELOG). The branch
  predictor learns start's `std::lower_bound` on a short table queried in the same order; head's
  compare is marked unpredictable, so it has no branch to learn.
- M4 `<string,u64>` n=32 `insert` 0.959: open, probably the index-based `insert`; not isolated. No
  issue filed.

**fs** (M4 15, i9 16)
- Every `normalize_path` row (M4 0.692 to 0.837 on 15 of 16; i9 0.447 to 0.877): fixed in
  `fs:c91b457` and `fs:f4439d8`. The three correctness fixes (an empty path, a default-constructed
  view, `..` popping the first component of a relative path) left it 1.3 to 2.2 times slower than
  start; the fixed loop makes one pass and builds the result on the stack. On an Apple M1 Pro
  every comparable row but `np_keep_slash` (0.95) is faster than start (`np_relative` 1.06,
  `np_dot` 1.4); not yet re-timed on the M4 Pro and the i9. `storage` and `url-parser` carry the same loop (`storage:f6e011c`,
  `storage:452aad9`, `url-parser:2a03c21`, `url-parser:eb0717e`).
- `np_empty`, `np_relative_pop`, `np_relative_pop_all` and the `copy_file` overwrite rows: not
  comparable (an empty path, a `..` that pops, `O_TRUNC`).

**fst** (M4 1)
- M4 `intersect`, 3-byte prefix, all keys, 0.953 (0.972 in the first hold): placement. `intersect`
  is unchanged; the new header code beside it moves it.

**http** (i9 2)
- i9 end to end, keep-alive, 64 connections 0.836 and 8 connections 0.856: the whole stack differs
  (see the geomean note). Fix in progress. Head's request parser is faster on both machines (1.253,
  1.327), and head's one-connection latency against Boost.Beast is
  [http#1](https://github.com/Kronuz/http/issues/1).

**io** (M4 1, i9 1)
- `pread_4K_tail_100B` (M4 0.543, i9 0.551): accepted. `io::pread` loops to the full count
  (`io:6524ce0`), so a read that reaches end of file makes a second `pread`, which returns 0
  (about 230 ns on the M4 Pro, 640 ns on the i9). Start returned after one call.

**logger** (M4 2, i9 2)
- Single-line latency, from an isolated `L_INFO` to the handler, median and p90 (M4 0.016 and
  0.029, i9 0.037 and 0.062): accepted. A line due within one 1 ms wheel tick is written 1 ms after
  the call, so producers rarely signal the LOG thread. These rows come from the gate's own
  micro-bench and are not in the geomean of 2.878 and 2.454. A change that
  writes an isolated line at once is in progress.

**lru-cache** (M4 1)
- M4 string keys, capacity 65,536, `lru::lru` 0.793: placement. The code is identical and the
  `std::list` + `unordered_map` control moved the same way (0.759).

**math** (M4 1, i9 4)
- M4 `modulus_u64` 0.954 and i9 `modulus_u32` 0.891: accepted. `modulus` tests for a zero
  modulus on every call, about 0.24 ns, and throws `std::invalid_argument` where start was
  undefined.
- i9 `modulus_i64` 0.958, `modulus_i64_by_i32` 0.965 and `add_u32_flag` 0.964: placement. The
  x86-64 code is identical, and the rows read 0.992 to 1.008 in a run with the rows in another
  order.

**msgpack** (M4 1, i9 1)
- M4 medium document `write` 0.953: placement. The unchanged msgpack-c rows move by the same amount
  (0.950), and with every function aligned to 64 bytes the row reads 0.98 to 1.00 (CHANGELOG).
- i9 small document copy after a fill 0.938: accepted. A fill merges repeated keys and checks the
  keys first; the CHANGELOG measures that check at up to 6%.

**scheduler** (M4 2)
- M4 "make only" with 1 producer 0.965 and 4 producers 0.909: accepted. `ScheduledTask` grew from
  48 to 96 bytes to carry `post()`'s hand-off fields. A smaller task is in progress.

**split** (M4 1)
- M4 iterator over 65,536 B with the `memchr` loop 0.946: placement. `split.h` is byte-identical.

**stash** (M4 2, i9 2)
- `steady D=64` p99 with 4 and 14 arming threads (M4 0.884 and 0.889, i9 0.928 and 0.924):
  accepted. `put` loads the leaf's claim hint and makes one compare-exchange on a leaf's first
  claim, and a leaf is 16 bytes larger (CHANGELOG). The same change removed a quadratic chain walk,
  which is most of the 1.745 and 1.800. On the i9 the rows are inside the spread in a second hold.

**storage** (M4 2, i9 3)
- M4 small blobs, lz4 write 0.704 and deflate write 0.915: accepted. `commit()` syncs the volume
  directory once after creating the file (`storage:217e731`), a durability fix; the CHANGELOG records
  the cost.
- i9 large blobs, whole read: lz4 0.719, zstd 0.763, deflate 0.789: fixed in `storage:890cc71`. A
  whole `read()` is sized once from the record and decoded in place; per MiB on the i9, start,
  gate head and now: lz4 929,661, 1,401,993 and 591,983 ns; zstd 1,198,584, 1,672,803 and 988,217;
  deflate 1,458,653, 1,942,153 and 1,060,176.

**strict-stox** (M4 6, i9 7)
- `stod` of 800 digits (M4 0.509, i9 0.429): not comparable. Start parsed only the first 63
  bytes; head parses all 800 and returns the right value.
- Declined text, which tries the fast path and then calls `strto*`: `inf, nan` (M4 0.808 and 0.825,
  i9 0.734 and 0.761), `" 1.5"` with leading space (M4 0.828 and 0.833, i9 0.820 and 0.854), `stoll`
  of 20 digits, `ERANGE` (M4 0.861, i9 0.881): accepted in `docs/perf/`. Fix in progress.
- i9 `stod` of odd integers between 2^53 and 2^54 (ties) 0.821: open, i9 only. Fix in progress.

**string-similarity** (i9 1)
- i9 Jaccard on 300 characters 0.750: placement. The kernel is unchanged, it reads 1.10 to 1.15 in
  an isolated build, and the M4 Pro reads 0.99.

**stringified** (M4 4, i9 4)
- Construction from a `std::string_view` plus `c_str()` (M4 0.051, i9 0.035) and the i9 copy of
  an owned 200-byte string (0.933): not comparable. Start's `c_str()` aliased the view, and its copy
  kept a view of the source.
- Move assignment of an owned 200-byte string, twice (M4 0.337, i9 0.663), move construction from
  a view (M4 0.611), and construction from a `std::string&&` of 10 bytes (M4 0.825, i9 0.901):
  accepted. Moves test whether the source owns its text and rebind, where start's shortcut
  dangled for small strings: 0.14 to 1 ns a call.

**strings** (M4 4, i9 1)
- `join(vector<string>)` of 2, 3 and 4 short strings (M4 0.920, 0.934 and 0.880; i9 0.893) and
  `replace` 1 to 3 characters, 256 B, 3 matches (M4 0.944): in the CHANGELOG. Fix in progress.

**threadpool** (M4 3, i9 3)
- `TaskGroup` burst of tiny tasks on 14 to 16 workers, wall, user and system time (M4 0.181 to
  0.608, i9 0.278 to 0.642): fixed in `threadpool:5d97d35`. A group lists one ticket at a time, and
  a worker runs the group's next task while only the group's tickets wait: 115 to 125 ns a task on
  4 to 16 workers of the M4 Pro (start 345 to 490) and 475 to 525 on the i9 (start 1,140 to
  1,950).
- i9 trickle, one task every microsecond, p99 delay 0.651 (0.617 in a second hold): the coalesced
  wake trades tail latency for CPU. Fix in progress.

**times** (M4 2, i9 3)
- M4 `timespec_t(double)` over an array, positive 0.917 and negative 0.918: accepted. Start's loop
  vectorized through `int`; head converts to `time_t`, which keeps whole seconds past `INT_MAX`,
  and borrows into a positive `tv_nsec`.
- i9 `double < timespec_t` 0.925: accepted. The comparison waits for the nanosecond conversion that
  makes the borrow (CHANGELOG).
- i9 chains through `tv_nsec` only, positive 0.821 and negative 0.827: open; head produces
  `tv_nsec` later (a 64-bit conversion, `trunc`, the borrow), not measured. No issue filed.
