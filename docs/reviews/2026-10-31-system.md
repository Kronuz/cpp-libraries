## Findings

### 1. One implementation per mechanism

F1. **escape and repr carry the same 100-line kernel.** escape.cc:45-133 and repr.cc:47-144 are the same `Tab`,
`make_tab`, `dirty8`, `measure`, `emit_byte` and `emit`, copied. `escape(p, n, q)` is byte-identical to
`repr(p, n, true, q, 0)`: 1,598,720 checks (every byte at every position of lengths 0-39, 200k random inputs in
three mixes, all four quote modes), 0 mismatches (probe not kept; covered by `char-classify:chars_escape_kernel`).
This is the drift the LESSONS summary blames on the original ("duplicated scanners that silently diverged"),
recreated. Who acts: char-classify, escape, repr. Fix: move the kernel into char-classify as a header (both already
depend on it, and `chars::char_repr` at chars.hh:271 is already the shared `\xNN` writer), so no repo gains a
dependency; escape and repr each keep their entry point and their frozen-copy differential.

F2. **Five private byte-class scanners, one of them SIMD.** url-parser has NEON/SSE2/SWAR `Scanner` (url_parser.cc:
143-200) with a `URL_PARSER_NO_SIMD` knob; repr/escape have SWAR-only `dirty8`; hashes has `swar_tolower`
(hashes.hh:308); prospect has an exact SWAR `spaces` (reader.hh:71); strings has an autovectorized
`ascii_lower/upper` (strings.hh:364-377). url-parser's SWAR fallback locates the hit bytewise because its zero-byte
test has false positives above the first hit (url_parser.cc:179-189), where prospect's form is exact. On x86 the
SWAR-only scanners give half the arm gain ([x86 survey](2026-10-30-survey-x86.md): repr 4 KB printable 3.0x on x86
against 5.7x on arm). A prototype that puts an SSE2 16-byte block test in front of escape's SWAR (same tables and
byte path, with an identity check over 900k inputs; prototype not kept) was ready for the i9 but was not timed (Not
run). Who acts: char-classify. Fix: one `chars` SIMD header in char-classify (find-first-of-N, "any byte outside a
range or equal to a set", ASCII case fold) with a `CHARS_NO_SIMD` knob and a portable CTest target, the convention
url-parser and docset already use; then url-parser, repr, escape and strings call it. hashes already depends on
char-classify and can adopt it when it next changes; prospect would gain an edge for one function, so it keeps its
own.

F3. **Two hex-digit tables.** url-parser built a byte table with a 0xff sentinel (url_parser.cc:109-116) beside
char-classify's `hexdigit` (chars.hh:139-160, 32-bit flags, 0xffffffff sentinel). Fix: add the byte table to
char-classify and use it from url-parser. sha256, md5 and cuuid keep their 16-character hex alphabets: adding
char-classify to md5/sha256 would be a new edge for ten lines (catalog rule 5).

F4. **XXH32: one implementation, guarded for one architecture.** compressors' kernel pins its four lanes to scalar
registers only on AArch64 (xxh32_stream.h:79); upstream xxHash 0.8.3 guards the same round on
`__SSE2__ || __aarch64__` (`xxhash.h:1874`). On x86 clang vectorizes the lanes at every level (`pmuludq` at x86-64,
`pmulld` at v2, `vpmulld` at v3; probe not kept), and so does g++-16 (four vector multiplies in the binary). On the
i9 the head is 1.4-2.1x slower than the same code with the guard on SSE2, on Apple clang 17 and g++-16 alike (table
in section 3). The README claims "upstream xxHash speed" without an architecture (compressors README, Performance).
Also `read32_le` assumes a little-endian host (xxh32_stream.h:66-73) while storage persists the digest on disk
(storage.h:319, 485-517): a big-endian host writes checksums a little-endian host rejects (pre-existing). Who acts:
compressors. Fix: extend the guard to `__SSE2__` and byte-swap on big-endian. Keep the kernel in compressors; moving
it into hashes would give compressors three transitive dependencies.

F5. **datetime keeps two calendar engines.** The new integer core (datetime.cc:71-90) serves parsing and date math;
the public `toordinal`/`timegm`/`timestamp` (datetime.cc:961-1060) still go through `cumdays`, `getDays_month` and
`normalizeMonths`. [Survey C](2026-10-30-survey-time.md) measured `timestamp(tm_t)` 4.2 ns against 1.8 ns for
days-from-civil. Fix: keep the validation and exceptions of `toordinal` and compute the ordinal as
`days_from_civil(y, m, d) + 719163`. Low priority; the one place a third copy could appear is logger's timestamp
formatter, which uses a cached `localtime_r` and does not need one.

F6. **Per-thread scratch has no family policy.** compressors caps its kept scratch at 1 MB per thread
(compressor_lz4.cc:461-492) plus a 16 KB LZ4 stream and zstd contexts; string-similarity's `Scratch::ensure`
(bitparallel.h:57-71) grows to `(distinct + 1) * ceil(n / 64)` words times 1.5 and never shrinks, per slot, per
thread: two 1 MiB strings through `Jaro` keep about 100 MB per thread for the thread's life (computed from the code:
257 rows of 16,384 words, times 1.5, per slot; probe not run, not kept; covered by
`string-similarity:string_similarity_scratch`). Who acts: string-similarity. Fix: keep at most a fixed amount per
thread (1 MB like compressors) and use a one-off heap block above it; state the rule once in the catalog.

Acceptable as is: three ten-line branchless lower bounds (flat-map, docset, metrics) for different key types, the
specialized open-addressing tables in generation-cache and the fst builder, and the small hash mixers in
generation-cache and cartesian. A shared header for any of them would add an edge for less code than the edge costs.

### 2. Consistency of the campaign's choices

F7. **datetime main is red, and its random inputs depend on the compiler.** Run 41235210764 on 03f36fa ("Fix month
normalization for multiples of 12"): linux-x86_64-gcc fails `datetime_diff` with 3 mismatches in 13,797,729 checks,
all `processDateMath` throw paths where the old intermediate `tm` had month 0 and the new one carries into month 12 of
the previous year (`-14y+13m+32s` on 5-24-13: old `{-7-0-13}`, new `{-8-12-13}`). The fix is right; the differential's
changed-class list misses "throw after a month carry". Only that one of the eight jobs hit it, most likely because the
generator draws in unsequenced operands (test/diff_test.cc:350, 367 and others:
`(chance(50) ? "+" : "-") + (chance(5) ? ...)`), whose evaluation order is unspecified and differs between compilers
and targets (GCC on x86-64 evaluates call arguments right to left), so the platforms test different input sets. Who
acts: datetime. Fix: add the class with the old != new assertion, and draw into named locals so every platform runs
the same inputs.

F8. **Build directories are committed.** datetime has `dbg/` (79 files, 5.4 MB: CMakeCache.txt with local paths,
four binaries) since 7acfefd; fst has `ubsan/` (68 files, 7.9 MB) since b08055f. fst is fetched by strata and
termdict with full history, so every consumer configure downloads it. Who acts: datetime and fst. Fix:
`git rm -r`, a `.gitignore` for build directories in both; rewriting history is an owner decision.

F9. **btree's work is invisible to consumers.** The default branch is `master` (25f9494); the campaign pushed
0d40c97, 4fc18b8 and a0b60e3 to `main`, which is strictly ahead of master by those 3 commits (compare API:
`ahead`). strata pins master (dd984d9). The campaign plan lists the consolidation as in progress. Fix: fast-forward
master to main, delete `main`, let CI run on master. The const-key relocation question (4fc18b8: moving a
`pair<const K, V>` key through `const_cast`) is an owner decision; absl's btree relies on a comparable layout trick,
so record which way it goes.

F11. **`[skip ci]` was used for a build change.** The docs-cleanup commits are comment-only in code (classified
above), but escape's also moved a FetchContent pin (CMakeLists.txt:12), which catalog rule 7 sends through the

F12. **Conventions that drifted.** Benchmark options come in five spellings: `<LIB>_BUILD_BENCH` (string-similarity,

F13. **The differential pattern is consistent; two gaps.** Every touched repo keeps a frozen copy in `test/`,

rapidfuzz oracle (test/rapidfuzz_check.cc), cited in the CHANGELOG as an oracle, is not a CTest test.

### 4. Risks to downstream consumers

F15. **Result-changing fixes, by consumer.** Consumers pin by SHA, so nothing changes until a bump; then:

| Library | Change | Consumer exposure | Where it is written |
|---|---|---|---|
| boolean-parser | implicit OR binds as a binary operator, left associative; malformed input rejected | Xapiand query_dsl.cc (`BooleanTree`): user queries such as `a AND b c` regroup; queries accepted before now fail | CHANGELOG, catalog |
| string-similarity | standard Jaro, real Jaro-Winkler, weighted Levenshtein, multiset Sorensen-Dice, PhoneticMetric | Xapiand sort keys (src/multivalue/keymaker.cc:635-690): similarity orderings change; serialised metric parameters still load | CHANGELOG, catalog |
| datetime | 5 quirks fixed, `+12M`, loose offsets set `is_utc` | Xapiand date fields: negative time fields no longer parse, a fraction dot with no digits no longer passes `isDatetime` (type detection), and `+12M` from December and a loose trailing `Z` now parse where they threw | README section (no CHANGELOG yet) |
| logger | routine lines written up to 1 ms after the call; a hard crash in that window loses them | Detent (four binaries), Xapiand | README, ARCHITECTURE; not the catalog entry |
| generation-cache | hash table, shared lock, per-table seed from `std::random_device` (can throw at construction) | Detent detentd diff cache | CHANGELOG |
| strict-stox, strings, stringified, repr, allocators | fixes of crashes, hangs and wrong rejections | fs, storage, msgpack, Detent, Xapiand | CHANGELOGs |

Each change is written in its repo, but no document tells a consumer "moving pin X to Y changes results for these
inputs". Who acts: cpp-libraries; the owner for Xapiand and Detent. Fix: one upgrade note in the catalog (library,
old and new SHA, the changed input classes, how to detect them), linked from each CHANGELOG entry, and a line in the
Xapiand and Detent bump commits. The boolean-parser and datetime rows are user-visible in Xapiand and want an
explicit owner decision at bump time.
